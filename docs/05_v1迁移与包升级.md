# v1、v2 迁移与工具升级

工具仓库不包含真实资产。v3 改变目录、状态与周统计，不直接打开 v2 配置写入，也不自动改旧目录。迁移在用户明确的独立资产之间完成，业务源码只读。

## v2 → v3

1. 先停止旧资产写入并备份旧目录（包含 .reqmgr）。确定新的空长期资产目录，旧目录保留；新旧、工具包、源码不可相互包含。
2. 用 v3 init 初始化新目录，source roots 与项目登记使用真实值。原资产 config.json 内 projects 可经 stdin register 到新资产，不复制包含原话的其他目录。
3. 预览，再导入，然后校验。下例路径必须换成真实绝对路径：

```bash
python3 -B scripts/reqmgr.py --asset-root /data/assets/requirements-v3 init --source-root /data/projects
python3 -B scripts/reqmgr.py --asset-root /data/assets/requirements-v3 register --stdin
python3 -B scripts/reqmgr.py --asset-root /data/assets/requirements-v3 migrate-v2 --v2-assets /data/assets/requirements-v2 --dry-run
python3 -B scripts/reqmgr.py --asset-root /data/assets/requirements-v3 migrate-v2 --v2-assets /data/assets/requirements-v2
python3 -B scripts/reqmgr.py --asset-root /data/assets/requirements-v3 validate
```

register 的标准输入由 AI 提供规范项目数组；无项目需求可省略登记。--dry-run 只读取规范记录和必要代码证据，输出新路径与修订数量，不写目标记录或日志；旧目录从不写入。

迁移保留旧稳定 ID、创建/更新时间、关联与 v2 全部有序修订，重新生成扁平路径、快照、索引与最新状态周表。新需求再用日期序号 ID。旧修订在新资产转成 v3 规范化快照，旧资产保留原始文件不动；不复制任何原话目录、聊天附件、任意额外 JSON 字段或旧生成 Markdown。

状态映射：未开始→未开始、未完成→进行中、已完成→已解决。旧待核实迁为未开始登记占位，同时明确“旧进度未知，需确认”，不能说已核实未实施；已解决仍保留既有完成依据。解决时间由历史状态进入完成的修订时间恢复。v2 未区分阻塞，不能猜测，迁后由用户反馈修订。迁移不会把“已确认”当已解决。

4. 查看索引、链接、数量、状态与修订；validate 通过后，将 REQMGR_ASSET_ROOT 或日常 --asset-root 改为新的固定路径。今后一直使用此 v3 资产。不要继续往新旧两套同时写入。

## v1 → v3

同样先初始化独立空目标并登记项目，再执行 migrate-v1 --v1-data 旧data绝对路径（支持 --dry-run）。只读取 records 与被引用的 sources，不读原话正文。v1 缺少实施进度，登记未知说明；只导入当前需求，legacy_revision/legacy_updated_at 保留来源，原 v1 历史仍在旧资产。

## 边界与恢复

目标已有需求、输出冲突、旧目录持有写锁、v2 当前记录与最新修订不一致时拒绝迁移。迁移不是整库事务；中断的 pending 日志可由 validate 检出，先备份与检查，不盲目重放。可丢弃失败的新目标并重新选择空目标；严禁删除旧资产作为恢复手段。

v3 以后更新工具包无需迁移，继续指向原 v3 资产。需要换资产磁盘路径时先停止写入、完整搬迁（含 .reqmgr），显式更新 config.json 的 asset_root 后核验；不静默创建另一份资产。
