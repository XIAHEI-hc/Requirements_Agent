# 状态颜色与每周总汇

| 状态 | Markdown 表示 | 使用依据 |
| --- | --- | --- |
| 未开始 | `⚪ 未开始` | 新登记初始化；历史未知需明确说明 |
| 进行中 | `🟡 进行中` | 用户反馈或只读依据 |
| 已阻塞 | `🔴 已阻塞` | 说明阻塞原因和依据 |
| 已解决 | `🟢 已解决` | 明确用户报告摘要或足够只读证据 |
| 已取消 | `⚫ 已取消` | 明确取消范围和依据 |

使用彩色图标+中文，不依赖 HTML style。字体由阅读器决定，不能保证文字本身染色。展示遵循用户周表样例。

## 固定周表结构

文件与需求同在工作周目录，名称固定 `本周需求总汇.md`。标题 `# 09.28-10.02 本周需求总汇`，随后工作周和北京时间最后同步时间。四个章节：

1. 状态统计：顶层需求、有效子需求、未开始、进行中、已阻塞、已解决、已取消。
2. 本周完整需求：编号、日期与标题、所属项目、状态、优先级、首次创建时间、最后更新时间、解决时间、当前进展、需求文件。
3. 大型需求与子需求进度：父条目链接，子项编号、标题、状态、验收标准、最后更新与解决时间、当前进展。没有时明确暂无。
4. 跨周补充与推进：旧条目在这个工作周的后续修订，记录当次状态、时间、规范化原因和原目录相对链接；注明 AI 未实施。

## 统计口径

归档周取 archive_week，既不按当前周重新分配，也不由后续更新时间改变。五个状态数**只统计该归档周顶层需求**，状态数之和等于顶层数量；有效子需求单独计数，不含已取消子项，不和父项重复相加。子项状态可在大型需求表逐项查看。

跨周更新不算本周新增、不进入本周完整需求表；它刷新原归档周表格，并出现在更新发生周的跨周章节。无更新的往周积压仅在总览和原周保留，不虚增本周数量。初次提前建档不是后续修订，不记为跨周推进。

历史周表持续显示**最新状态**，最后同步时间是本次生成时间，不是历史周末截点。需要看某时点的状态，应查看修订历史。用户反馈后来完成，即更新原周状态及解决时间。仅改标题不会改变解决时间；重新打开会清空当前解决时间，再次解决记新解决时间，旧解决仍在历史中。

## 父子需求与依据

children 的每项有稳定编号与独立验收标准，取消保留痕迹，不直接删除。父项/子项不自动联动；只有用户明确覆盖所有子项的完成反馈才能逐项登记依据，再将父项解决。子项全部解决也不自动推断父项完成，父项可能还需整体验收。

progress 为统一主状态，status 的旧确认枚举仅内部兼容；输入 status=五种主状态也可，不能与 progress 矛盾。状态变化必须新填 progress_source 和 progress_note。解决必须有 completion_evidence，注明用户报告是否独立验证。Agent 不运行任何业务代码、测试或部署来查进度。

apply、reindex、weekly 会刷新全部已知周；weekly --week 可指定空周，未来重建保留。没有安装周期定时任务。
